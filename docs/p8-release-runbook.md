## 3. プリフライト（A1a → A1b → A1c → 必要なら A1d）

**実行の仕方**。読み取り専用の確認ファイルは 2 種類あり、psql の書き方が違う（PostgreSQL では、トランザクションの中で `BEGIN` を出しても警告になるだけで、ファイルの `ROLLBACK` は psql が始めたトランザクションを途中で終わらせる）。

| 種類 | ファイル | psql | SQL Editor |
| --- | --- | --- | --- |
| **T0**: 自分ではトランザクションを開かない（先頭が `set transaction read only;`） | A1a〜A1d（`supabase/preflight/P8_*`）、C1 `P8_state_check.sql`、`supabase/drafts/0028_timezone_lookup.checks.sql` | `psql -X -1 -v ON_ERROR_STOP=1 -f <ファイル>`（`-1` が必須） | ファイル全体を 1 回で実行 |

使わない書き方と、その理由（隔離環境で実測）:

| 書き方 | T0 | T1 |
| --- | --- | --- |
| `ON_ERROR_STOP` なしの `psql -f` | ゲートでエラーになっても、後ろの文が読み取り専用・時間制限なしで実行された | ファイル自身の `BEGIN` があるので読み取り専用。読み取り専用を外した版では、ゲートのエラーの後の文は「トランザクションが中断済み」で実行されなかった。それでも使わない |
| T1 に `-1` を付ける | — | 二重の `BEGIN` の警告。18.6 では結果的に読み取り専用になりゲートも通ったが、文書化された動きではないので頼らない |
| SQL Editor で一部だけを選んで実行 | ゲートを飛ばせてしまう | 同じ |

**ゲートの仕組み**（各ファイル共通）:
- 先頭の 2 行（`set transaction read only;`・`set local statement_timeout = …;`）の直後に**ゲートの文**がある。

**関数本文の指紋**（A1a の F01・F02、C1、0028 のガード、0028 の確認の C02）は、`prosrc` の **CRLF を LF に変えてから** md5 を取り、リポジトリのファイルから作った本文の指紋と比べる（0018・0027 の確認 SQL と同じ考え方）。
SQL Editor に Windows の改行のまま貼ると本文に CR が残り、psql で送ると残らない（隔離環境で実測）。どちらも同じコードなので同じ指紋になる。

- 本番の A1a（2026-10-21）は改行の正規化の前の版で、F01・F02 が GATE-FAIL だった。報告された md5（`2fe6af14…`・`8b11e3d1…`）は、隔離環境で 0006・0008 の本文を CRLF にした md5 と**完全に一致**した。つまり本番の本文は、改行コード以外はレビューしたものと同じ（本番への追加の接続はしていない）
- 本番の md5 を許可リストに足す方法は取らない。正規化の後は、LF の本文・CRLF の本文のどちらも同じ指紋（`2e59e479…`・`d6d46c84…`）で合格し、意味を変える変更（長さの上限、拒否する名前、返す状態の文字列）、CR だけの改行、行末の空白は、すべて GATE-FAIL になった

**復旧の成功の条件**: 確認スクリプトの結果が、停止前に保存したものと同じ（ACL は並び順に依らない形で比べる）。

隔離環境での確認: 通常（レベル 1・2 とも停止・復旧、復旧後の結果が停止前と一致）、PUBLIC 経由・所属経由（中止し何も変わらない）。

**他の停止手段（環境に依存。いずれも本番未確認。実装したものではない）**

| 手段 | 効果 | 制約・確認方法 |
| --- | --- | --- |
| Supabase の Auth で新規登録を止める | 新しい所有者を増やせなくなる（K15 の書き込み側） | ダッシュボードの Auth 設定。既存の利用者には効かない |
| Supabase プロジェクトの一時停止 | すべて止まる | ダッシュボード。アプリ全体が止まる |
| API キーの無効化・再発行 | そのキーでの REST・RPC がすべて止まる | アプリ自身も同じキーを使うので、アプリ全体が止まる。キーの方式（従来の anon キーか、新しいキー）を要確認 |
| ネットワーク制限 | DB への直接接続を制限 | REST（PostgREST）経由のアクセスに効くかは要確認 |
| edge でのリクエスト数制限 | 1 IP・1 トークンあたりの回数 | Supabase の機能・プランで何が使えるかは要確認 |

## 8. tzdata の更新と 0028 の一覧

Supabase の PostgreSQL・OS が更新されたら、`supabase/drafts/0028_timezone_lookup.checks.sql`（読み取り専用）を実行する。

| 行 | 意味 | GATE-FAIL のとき |
| --- | --- | --- |
| C03 | サーバーが知っているのに一覧に無い名前（tzdata で**追加**された） | そのゾーンでの時刻つき繰り返しの保存が `TIMEWEAVE_TZ_INVALID` で拒否されている。0028 を所有者ロールで再実行して一覧を作り直す（隔離環境で修復を確認） |
| C04 | 一覧にあるのにサーバーが知らない名前（tzdata で**削除**された） | 書き込みは通るが、共有側の `timezone_is_resolvable` が拒否するので答えは fail-closed（隔離環境で indeterminate を確認）。0028 を再実行して作り直す |
| C06 | 実行権限が `timezone_is_supported` と違うロールの数 | 0028 を再実行（権限を写し直す） |
| C08 | 一覧の関数の本文が、0028 が書く形（`select $1 = any ('{…}'::text[])`）と完全に同じか | 形が違えば一覧を読み出さず GATE-FAIL（空の一覧として誤って合格させない）。誰かが書き換えた可能性があるので止まって報告 |
| C05・C09・C10 | 件数が等しく 0 でない・重複が無い・サーバーの全名前で真を返し、存在しない名前で偽を返す | 0028 を再実行して作り直す。直らなければ止まって報告 |
| C11 | 一覧の関数が SECURITY INVOKER・STRICT・PARALLEL SAFE・LANGUAGE sql・`search_path=""` だけの設定で、所有者が `timezone_is_supported` と同じか | 誰かが変えた可能性がある。止まって報告（0028 の再実行は所有者を戻さない） |

C03・C04 は一覧を**集合として**比べる（件数だけの比較では、1 つ欠けて 1 つ重複した一覧を見逃す）。
隔離環境で、一覧の関数を 8 通りの誤った定義（空の配列、1 件欠け、1 件余分、件数を保った重複、`ARRAY[…]` という別の書き方、一覧を使わない本文、一覧の後ろに条件を足した本文、IMMUTABLE でない）に置き換えたところ、
**8 通りすべてが GATE-FAIL** になり、C1 も `APPLIED-DRIFTED` または `INCONSISTENT` を返した。0028 を再実行すると、どれも GATE-OK に戻った。

別名（`US/Eastern` など）は `pg_timezone_names` にある限り一覧にも入る。本番A1cで**1196行**を観測（隔離環境の約598行を本番の上限や期待件数として固定しない）。
**放置した場合の影響は、新しいゾーンの利用者が時刻つき繰り返しを保存できないところまで**（漏えい・データ破損はない）。
