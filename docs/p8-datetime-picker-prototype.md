## 1. 現在の実装と、入力UIを差し替えるための境界

### TimeWeave の日時の持ち方

| 段階 | 形式 | 場所 |
| --- | --- | --- |
| DB・API | UTC ISO 8601 | `start_at` / `end_at`（時刻あり）、`start_date` / `end_date`（終日・終了は排他） |
| フォーム状態 | **ローカル壁時計の文字列** | `EventDialog.tsx:187-188` `startLocal`/`endLocal` = `"YYYY-MM-DDTHH:mm"`、`startDate`/`endDateInclusive` = `"YYYY-MM-DD"`、`RecurrenceEditor` の `untilDate` = `"YYYY-MM-DD"` |
| 読み込み時 | ISO → 文字列 | `toDatetimeLocalValue` / `toDateInputValue`（`utils/datetime.ts`） |
| **保存時のみ** | 文字列 → ISO | `buildSaveResult` 内の `isoFromDatetimeLocalValue` / `isoFromDateString`（`EventDialog.tsx:356-398`）。終日の終了は `addDaysToDateString(+1)` で排他に |
| 繰り返し | until 日付 → オーナーのTZで解釈 | `recurrenceForm.ts` `formToRule(form, dtstartIso, timeZone, allDay)`（`endOfZonedDayIso`） |

変換は**ブラウザのローカルTZ**で `new Date("YYYY-MM-DDTHH:mm")` を使う
（`isoFromDatetimeLocalValue`）。繰り返しのTZ（`timezone` 列）は別系統で、
入力欄の値とは独立に `resolveStorableTimeZone` から与えられる。

### 境界（ここだけ差し替えればよい）

> **入力部品は「`"YYYY-MM-DDTHH:mm"` / `"YYYY-MM-DD"` の文字列を受け取り、確定した
> 文字列を返す」だけでよい。**

- 現在の `<input type="datetime-local">` の `value` / `onChange` と**同じ契約**
- 部品は瞬間（instant）もTZも扱わない。ISO化・DST・繰り返しのTZは今までどおり
  `buildSaveResult` と `utils/datetime.ts` / `recurrenceForm.ts` が行う
- 試作の3候補はすべてこの契約で実装し、`src/model.ts` の `simulateSave` が本物の
  `utils/datetime.ts` を通して ISO を出している（画面の「保存を試す」）

部品が追加で持つべき唯一の情報は **「入力中の値が不正」** という状態
（試作の `onInvalid`）。現行ネイティブはこれを `''` で表すため、保存時に
「日付を入力してください」になる（P8-b5で導入した検証）。

## 5. 試作で見つかったこと

1. **A と C は入力途中の値を確定値として外に出す。** 分に `45` と打つと、1打目で
   `14:04` が `onChange` される（記録に残る）。終了追従を入れると、その途中値で
   終了まで動く。B は blur/Enter まで確定しない
2. **A は Delete 1回で値全体が `''` になる**（P8-b5 で既知）。B は欄単位で赤くなり、
   確定値は保持
3. **C はピッカー操作中も `onChange` を出す**（Desktop・Mobile とも）。キャンセル時は
   元に戻す `onChange` が後から来る。本体に入れるなら `onAccept` で確定し、
   `onChange` はフィールド入力だけに使う設計が必要
4. **1分単位のタップは狙えない。** 時計盤で 1分 = 6° ≒ 4px（PC）/ 11px（320px）。
   「45」を狙ったクリックが `:43` になった。B は「タップ=5分刻みにスナップ、
   ドラッグ=1分単位、±1ボタン/矢印キー」に変更した。**この挙動自体を評価してほしい**
5. **MUI X の「タイムゾーン非対応」は、この境界では障害にならない。** P8-b5 の評価は
   「AdapterDateFns はTZ非対応 → 決定的」としていたが、試作では部品にTZを一切渡さず
   壁時計の値だけを編集させ、ISO化は従来どおり `utils/datetime.ts` が行う構成で
   問題なく動いた。**MUI X のTZ機能（Day.js/Luxon/Moment 限定）と、TimeWeave への
   統合可能性は別の話**で、後者は「壁時計として使う限り可能」。ただし下記 §6 の
   DST のずれは残る
6. **英語ブラウザでの 24時間表記**は A だけの問題（ブラウザのロケール依存）。
   B と C はアプリ側で固定できる

## 6. タイムゾーン・DST の統合リスク

### 現行の変換（Node で `TZ=America/New_York` を設定して実測）

| ケース | 入力 | 保存される瞬間 | 表示に戻すと |
| --- | --- | --- | --- |
| 存在しない時刻（春の切替） | `2026-03-08T02:30` | `07:30Z` | **03:30**（黙って1時間後ろへ） |
| 重複する時刻（秋の切替） | `2026-11-01T01:30` | `05:30Z` | 01:30（**先の方＝EDT** を採用） |

これは**現行の `isoFromDatetimeLocalValue` の挙動**で、どの候補でも保存時に同じこと
が起きる（候補は文字列を返すだけなので）。日本（Asia/Tokyo）にはDSTがないため
日常では現れない。

### 候補ごとの差

| | リスク |
| --- | --- |
| A | 変化なし |
| B | 変化なし。時計は時・分の数字しか扱わず、存在しない時刻も文字列としてはそのまま返す（保存時に上記の変換） |
| C | `AdapterDateFns` は値を**ローカルの `Date`** で持つ。存在しない時刻は部品の中で `Date` 化された時点で 03:30 に**入力中に書き換わる可能性**がある（DST のある TZ で未検証）。重複時刻は `Date` が先の方を選ぶ |
| C で Day.js/Luxon の TZ 機能を使う場合 | date-fns-tz と意味論の違う日付ライブラリが2系統になる。**推奨しない**（P8-b5 の判断を維持） |

### 開始・終了の連動（試験機能。本体には未導入）

試作の「開始に終了を追従」は3方式を切り替えられる。

| 判断点 | 内容 |
| --- | --- |
| 何を維持するか | **壁時計の長さ**（14:30–15:30 の「1時間」）か **経過時間**（ミリ秒）か。DST 当日だけ結果が変わる。例: NY で 01:00 開始・60分の予定を、経過時間で維持すると終了は 03:00（壁時計では2時間に見える）。壁時計で維持すると 02:00 になるが存在しない時刻なので保存時に 03:00 |
| 日付またぎ | 試作は自然に翌日へ繰り上げる（23:30 開始 → 終了 00:30 翌日、実測） |
| いつ追従するか | 確定した開始の変更だけ。**A/C は途中値でも確定扱いなので、入力中に終了が動き回る**（B では起きない） |
| 不正な元の組 | 元の終了 < 開始なら追従しない（維持する長さが無い） |
| 終日 | 開始日の移動日数ぶん終了日をずらす（`addDaysToDateString`）。日単位なので DST の影響なし |
| 終日 ⇄ 時刻の切替 | 追従の対象外（切替時の終了の決め方は現行のまま） |
| 繰り返し | dtstart が動くと until との関係・例外日（EXDATE）との対応が変わる可能性。**本体統合時に要検討** |
| 終了を手で変えた後 | 試作は「次に開始を動かしたときの長さ」を新しい長さとして使う |

## 7. 推奨案（ユーザー評価の前の暫定）

**第一候補: B（軽量カスタム）を本体へ。** 理由:

- 要望の「入力途中で書き換わらない」「`14:30` を自然に打つ」「コピペ」を満たすのは B だけ
  （A と C はセグメント入力で、途中値を確定する）
- 依存 0・約 8 KB。本体の方針（UIライブラリなし・手書き CSS）と矛盾しない
- 境界は現行と同じ文字列契約なので、保存・TZ・DST・繰り返しのコードに触れずに差し替えられる
- 日付のカレンダーはブラウザ標準を使い、独自のカレンダー計算を持たない

**C を選ぶ場合の条件:** 見た目と操作の完成度を重視し、+約140 KB と CSS-in-JS の
同居を許容する場合。`onAccept` で確定する統合が前提。

**A を維持する場合:** 操作感の改善より依存・保守の最小化を優先する場合。
英語ブラウザの AM/PM と途中値の確定は残る。

**ただし最終判断はユーザーの操作感で決める。** 特に B の「タップ=5分スナップ」、
時計シートの位置、文字入力への切替の分かりやすさは、実機で触ってみないと評価できない。

## 2. 日付入力 — 確定時正規化（既定）と自動ハイフン（比較用）

**採用: 確定時（blur / Enter）に正規化。** 入力中は打った文字をそのまま保持し、
カーソル位置も値も変えない。`20261019` → Tab で `2026-10-19`。

比較のため「日付の自動ハイフン（比較用）」を用意した（既定オフ）。

| 観点 | 確定時正規化（既定） | 自動ハイフン（比較用） |
| --- | --- | --- |
| `20261019` を打つ | `20261019` のまま → 確定で `2026-10-19` | `2026` で `2026-` に、`202610` で `2026-10-` に変わる |
| ハイフンを手で打つ | そのまま | 直前に自動で入れたハイフンと重なる場合だけ握りつぶす（`2026--` にならない。実測） |
| 途中の挿入・Backspace | 自然（実測: 中央で Backspace→挿入しても caret 6→7、末尾へ飛ばない） | 末尾で数字を打った時**だけ**動くので、途中編集・Backspace・貼り付けは無干渉。ただし **Backspace でハイフンを消した後に数字を続けると区切りは戻らない**（`2026-10` → `2026-102`、形式エラーになる） |
| スラッシュ派 | そのまま | 触らない |
| 実装の複雑さ | なし | `inputType`・caret 位置・直前値の3つに依存（`autoHyphen()`、テスト8件） |

時刻のコロンは**自動挿入しない**。`93` の時点で `09:3x` なのか `9:30` の途中なのかが決まらず、

## 5. DST 判定（試作のみ。本体の保存には未適用）

### 方式

`src/dst.ts`。**対象タイムゾーンを引数で受け取り**、OS のタイムゾーンは参照しない。

1. 壁時計の値の前後 36 時間での、そのタイムゾーンの実際のオフセットを `Intl`（`formatInTimeZone`）から得る
2. オフセットごとに候補の瞬間を作り、**同じタイムゾーンで表示し直して元の壁時計と一致するものだけ残す**
3. 残った数で判定: 1＝通常、0＝存在しない、2＝二重
4. 存在しない時刻は、切替の瞬間を 1 分単位の二分探索で特定する（「1時間ずれる」と仮定しない。Lord Howe の 30 分切替もテスト済み）

### 調査で分かったこと（重要）

**本体の2つの変換経路が、DST で逆方向に補正する**（America/New_York、実測）:

| 入力 | `new Date()`（`isoFromDatetimeLocalValue`、予定フォーム） | `fromZonedTime()`（`utils/timezone.ts`、スロットクリック・繰り返し until） |
| --- | --- | --- |
| 2026-03-08 02:30（存在しない） | 03:30 EDT（**後ろへ**） | 01:30 EST（**前へ**） |
| 2026-11-01 01:30（二重） | 01:30 EDT（**1回目**） | 01:30 EST（**2回目**） |

どちらも必ず何らかの瞬間を返すので、**変換が成功したことは存在の証拠にならない**。

**`date-fns-tz` の `getTimezoneOffset(zone, date)` は使えない。** JST の PC で
`2026-11-01T04:30Z` の New York を `-5h` と返した（正しくは EDT の `-4h`）。
Date の OS ローカルの値を読んでいるため、切替の近くで別の瞬間の答えを返す。
試作では使わず、`formatInTimeZone` の往復でオフセットを求めた。本体はこの関数を使っていない（grep 確認済み）。

判定は、OS のタイムゾーンを UTC / America/Los_Angeles / Europe/London / Australia/Sydney に
変えても同じ結果になることを確認した（Node で `process.env.TZ` を切替）。
なお、この PC の Chrome は OS のタイムゾーンを `Etc/GMT-9` と報告する（`Asia/Tokyo` ではない）。

### 画面での挙動（ブラウザで実測）

| 例 | 結果 |
| --- | --- |
| 通常 NY 2026-10-18 14:30 | 「通常」UTC−04:00 EDT → 18:30Z |
| 春 NY 2026-03-08 02:30 | 「存在しない時刻」。「01:59 EST の次が 03:00 EDT（60分進む）」と説明。**保存は止まり、02:30 は書き換えない**。参考として、本体の関数なら黙って 01:30 EST になることを表示 |
| 秋 NY 2026-11-01 01:30 | 「二重に存在する時刻」。未選択のまま保存すると「1回目か2回目を選んでください」。**1回目＝01:30 EDT (UTC−04:00) → 05:30Z、2回目＝01:30 EST (UTC−05:00) → 06:30Z**。どちらも再表示で 01:30 に戻る（✓） |
| 東京 2026-03-08 02:30 | 通常（同じ壁時計でもタイムゾーンで答えが変わる） |
| London / Sydney / Lord Howe | 二重・存在しない・30分の切替をそれぞれ確認（テスト） |

二重時刻の選択は「どの壁時計の値に対する選択か」と一緒に保持し、値を変えると選択は消える。

### 別途仕様判断が必要なこと

- **終日予定**は日付だけなので判定対象外。ただし繰り返しの until はオーナーのTZの
  「その日の終わり」に変換されており（`endOfZonedDayIso`）、ここは `fromZonedTime` 経路
- **繰り返し予定**: 開始が二重/存在しない時刻の場合、各回で同じ問題が起きる。RRULE の展開側
  （どの回を 1回目/2回目にするか、存在しない回をどうするか）は本試作の範囲外
- **単発の時刻指定予定**は現状ブラウザ（OS）のTZで解釈されている。「予定の対象TZ」を持たせるかは未決定

## 6. 開始・終了の連動

P8-b5.6a の3方式（オフ／壁時計／経過時間）を維持。**経過時間は対象TZで計算する**ように変えた
（以前はブラウザのTZ）。比較表は画面の DST パネル下部にあり、「読込」でフォームに入れて再現できる。

| 例（America/New_York） | 前 | 新しい開始 | 壁時計の長さを維持 | 経過時間を維持 |
| --- | --- | --- | --- | --- |
| 通常の日 | 10/18 14:30→15:30 | 15:00 | 16:00 | 16:00（同じ） |
| 春: 開始を切替の直前へ | 3/8 00:30→01:30 EST | 01:30 | **02:30 = 存在しない時刻**（保存で止まる） | **03:30 EDT** |
| 春: 切替をまたぐ予定を前日へ | 3/7 22:00→3/8 04:00（壁6h・実5h） | 3/6 22:00 | 3/7 04:00 | **3/7 03:00** |
| 秋: 終了が二重の時間帯に入る | 11/1 00:00→01:00(1回目) | 00:30 | 01:30（**1回目/2回目が決まらない**→要選択） | 01:30 **1回目**（瞬間から自動で決まる） |
| 秋: 二重の時間帯をまたぐ | 11/1 00:30→01:30(2回目)（実2h） | 00:00 | 01:00（要選択） | 01:00 **2回目** |

予期せぬ変更を防ぐため、次の場合は**終了を動かさず**、理由を表示する:
元の開始/終了または新しい開始が「存在しない」「二重で未選択」、元の終了が開始より前、値が不完全。
ブラウザで「春: 開始を切替の直前へ」を読み込み、開始を 01:30 に変えて、経過時間 → 03:30、
壁時計 → 02:30（存在しない時刻の表示）になることを確認した。

## 11. P8-b5.6b-2（本体統合）への申し送り

- 部品の契約は従来どおり「`"YYYY-MM-DDTHH:mm"` / `"YYYY-MM-DD"` を受け取り、確定値を返す」＋「不正な下書きがある」通知。`buildSaveResult` 以降は変えない想定
- 本体へ持っていくのは `src/custom/`（`timeParse.ts`・`calendarMath.ts`・`GuidedInput`・`CalendarPicker`・`ClockDialog`・`fields`）。文言は本体 i18n へ
- DST 判定（`dst.ts`）は**別タスク**として扱う（R1〜R4 の仕様判断が先）。保存処理へ無断で適用しない
- 終了の追従は仕様変更。入れるなら「経過時間方式＋未解決時は動かさない」が試作からの結論候補
- 本体の vitest は jsdom を使わない方針なので、統合時もパーサ・カレンダー計算・DST 判定は純関数のまま node でテストする
- 試作で見つけた不具合（フォーカス失敗、Enter での再オープン、エラー文の差し込み、末尾追記）は統合時の回帰項目にする
