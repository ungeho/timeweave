## 3. DST 変換の実測（呼び出し元・入力・OS タイムゾーン・対象タイムゾーンを分けて）

対象タイムゾーン `America/New_York`。Node で `process.env.TZ` を切り替えて計測。
`new Date` は「OS = 対象」の場合だけ意味がある（OS の解釈しかしないため）。

| 入力 | `new Date`（OS = NY）※予定フォーム | `fromZonedTime`（OS = NY / UTC / London） | `fromZonedTime`（OS = Tokyo / Sydney） | `resolveZonedWallClock`（展開・どの OS でも） |
| --- | --- | --- | --- | --- |
| 03-08 02:30（存在しない） | 07:30Z = **03:30 EDT** | 06:30Z = **01:30 EST** | 06:30Z = 01:30 EST | 07:30Z = 03:30 EDT |
| 11-01 01:30（二重） | 05:30Z = **1回目 EDT** | 05:30Z = **1回目 EDT** | 06:30Z = **2回目 EST** | 06:30Z = 2回目 EST |
| 10-18 14:30（通常） | 18:30Z | 18:30Z | 18:30Z | 18:30Z |

**P8-b5.6b-1 の報告の訂正:** 試作では「`fromZonedTime` は二重時刻で2回目」と書いたが、それは
**JST の PC で測った結果**で、OS が NY / UTC / London なら1回目を返す。`fromZonedTime` の二重時刻の
答えは **OS のタイムゾーンに依存する**。存在しない時刻は OS に関係なく「前（01:30 EST）」。

本体の実際の呼び出しでは「対象 = OS」（`getUserTimeZone()` を渡している）なので、NY の PC では:

| 経路 | 存在しない 02:30 | 二重 01:30 |
| --- | --- | --- |
| 予定フォームの保存（`new Date`） | 03:30 EDT（後ろへ） | 1回目 |
| 空き枠クリックの初期値（`fromZonedTime`） | 01:30 EST（前へ） | 1回目 |
| 繰り返しの展開（`resolveZonedWallClock`） | 03:30 EDT（後ろへ） | **2回目** |

**どの経路も必ず何らかの瞬間を返すので、変換が成功したことは時刻が存在する証拠にならない。**

## 4. 見つかった不具合とリスク

### B1（既存の不具合・今回直る）: 二重時刻の予定をタイトルだけ編集すると1時間前にずれる

保存済みの瞬間が「2回目」（例 06:30Z）の予定・発生回を NY の PC で開くと、`toDatetimeLocalValue` が
`01:30` を作り、保存時に `new Date("…T01:30")` が「1回目」（05:30Z）を返す。**時刻に触っていないのに
保存で1時間動く。** 2回目の瞬間は、繰り返しの展開（「後の瞬間」規則）で日常的に生まれる。

統合後は、開いた時に保存済みの瞬間から「どちらの回か」を復元し、時刻を変えなければ同じ瞬間を保存する。

### B2（既存の不具合・今回直る）: 存在しない時刻が黙って別の時刻で保存される

NY の PC でフォームに 02:30 と入れると 03:30 EDT で保存され、再表示は 03:30。説明が無い。
時刻つき繰り返しの DTSTART なら、以後の全回が 03:30 になる。統合後は入力エラーにする。

### R1（既存のリスク・今回は触らない）: `fromZonedTime` の二重時刻が OS に依存する

使っているのは `dayStartInstantIso`（日の範囲・共有の配置・繰り返し終了日の「その日の終わり」）と
`instantFromZonedDayMinutes`（空き枠クリックの初期値）。本体は「対象 = OS」で呼ぶので、
現状の利用では OS 依存の差は表に出ない。ただし**深夜 0 時に切り替わるタイムゾーン**
（例: 一部の南米・中東）では、日の始まり自体が存在しない/二重になり、日の範囲が1時間ずれ得る。
未検証・未修正。直すなら `resolveZonedWallClock` 系への置き換えで、表示範囲と共有の配置が変わるため別承認が要る。

### R2（既存のリスク・今回は触らない）: 経路ごとに補正方向が違う

上表のとおり。統合後のフォームは存在しない時刻を拒否し、二重時刻は明示的に選ばせるので、
**フォーム経路では黙った補正が無くなる**。展開（「後の瞬間」）と空き枠クリックの初期値（「前」）は既存のまま。
空き枠クリックの初期値は保存前にダイアログで見える値なので、黙って保存されるわけではない。

### R3（既存のリスク・今回は触らない）: 共有リンクの有効期限

ネイティブ `datetime-local` + `new Date` のまま。存在しない時刻は黙って後ろへずれる。任意項目で、
B2 と同じ修正は可能だが、共有ダイアログは今回の範囲外。

### R4（仕様の確認）: 時刻つき繰り返しの壁時計の帰属

フォームの壁時計は **OS のタイムゾーン**、展開は **マスターの `timezone`**。両者が違う場合
（作成後に別のタイムゾーンへ移動した等）、フォームの DST 判定は OS 側で行う（変換が OS 側で起きるため）。
展開側の解決は変えない。

## 5. Step 2: DST の統合可否

### 判定: **既存の保存形式のまま、安全に統合できる**

| 方針 | 実現方法 | 既存への影響 |
| --- | --- | --- |
| 通常の時刻 | **`isoFromDatetimeLocalValue` をそのまま使う**（コードを変えない） | なし。同じ瞬間 |
| 存在しない時刻 | 保存前に検出し、入力エラー（理由と直し方）で止める | 新しい検証。保存済みの瞬間は必ず実在する壁時計に戻るので、**既存データを開いただけでは出ない** |
| 二重時刻 | 1回目/2回目を UTC オフセット付きで選ばせ、選んだ瞬間を保存 | `start_at`/`end_at` は瞬間なので選択が永続化される。再編集時は保存済みの瞬間から復元 |
| 繰り返し | DTSTART は保存済みの瞬間のまま使われる（展開は再構成しない）ので選択が保たれる。以後の回の解決（「後の瞬間」）は変えない | 展開・SQL・共有に変更なし |
| 終日 | 対象外（暦日） | なし |

### 誤判定を防ぐ二重確認

判定は `Intl` で対象タイムゾーン（= `getUserTimeZone()`）の候補の瞬間を数える方式（2.4 と同じ原理）。
加えて、**`Date`（実際に保存に使う変換）が同じ結論のときだけ介入する**:

- 存在しない: `Date` で変換して戻すと別の壁時計になる、を併せて確認
- 二重: 2つの候補が `Date` のローカル表示でも同じ壁時計になる、を併せて確認

`Intl` の解決値と `Date` の解釈が食い違う環境（このPCの Chrome は OS を `Etc/GMT-9` と報告する）
では、介入せず従来の変換に任せる。**判定が間違って保存できなくなる事故を避けるため。**

### テスト計画

- 判定（純関数）: Asia/Tokyo 通常、NY 春の欠落・境界前後（01:59/02:00/02:59/03:00）、NY 秋の二重・境界前後、
  London・Sydney・Lord Howe（30分）、対象タイムゾーンを引数で変えた場合
- 保存相当の変換: OS タイムゾーンを NY / Tokyo に切り替えて、通常時刻が `isoFromDatetimeLocalValue` と
  **完全一致**すること、二重の選択がそれぞれの瞬間になること、欠落が拒否されること、往復（瞬間→表示→判定→同じ瞬間）
- 既存予定の再編集: 2回目の瞬間を持つ予定から選択が復元され、時刻に触らない保存で同じ瞬間になる（B1）
- 既存テスト（`resolveZonedWallClock`・展開・共有）は**期待値を変えない**

## 9. R1: 日付範囲と深夜0時の切り替え（P8-c1・2026-10-19）

### 契約（今回明文化）

**ゾーン Z の暦日 D の範囲は半開区間 `[D の始まり, D+1 の始まり)`。D の始まりは「Z での壁時計の日付が D 以降になる最初の瞬間」。**
1日が24時間とは仮定しない。

| 深夜0時の状態 | D の始まり |
| --- | --- |
| 普通にある | その瞬間 |
| 存在しない（時計が 23:59:59 → 01:00:00） | 時計が飛ぶ瞬間（最初に存在する時刻） |
| 2回ある（01:00 → 00:00 に戻る） | **1回目** |
| 日付ごと存在しない（Pacific/Apia 2011-12-30） | 翌日の始まりと同じ（長さ0の日） |

これは JavaScript の `Date` がローカルの深夜に与える解釈と同じで、月表示（`monthGrid.ts` の `new Date(y, m, d)`）は
もともとこの規則だった。サーバーの終日予定の変換（0025 の `d::timestamp at time zone Z`）も、存在しない深夜は
「進める」側で一致する（2回ある深夜だけ下記 R1-S のとおり異なる）。

### 再現（修正前）

57 ゾーン・502 件見つけた。代表例と、修正前の `dayStartInstantIso`（`fromZonedTime`）の結果:

| Pacific/Apia 2011-12-30 | 12-29 23:59:59 の次が 12-31 00:00:00 | 12-29 の 0:00（29日を丸ごと飲み込む） | 長さ0（12-30T10:00Z） |

### 根本原因

1. `dayStartInstantIso` が `fromZonedTime(D + 'T00:00:00')` だった。`fromZonedTime` は存在しない時刻を前へずらし、
   2回ある時刻の選択が OS のゾーンで変わる（P8-b5.6b-2 §3 の実測と同じ）
2. 壁時計の読み取り（`zonedDayKey`・`zonedMinutesOfDay`・`zonedWallMsAt`）が `formatInTimeZone` だった。これは
   ゾーンの壁時計を **OS ローカルの Date** に入れて書式化するため、その壁時計が OS のゾーンで存在しない時刻だと
   1時間ずれる（**実測: OS=New_York で、東京の 2026-03-08 02:30 を 03:30 と読んだ**）
3. `addDaysToDateString` が OS ローカルの Date で日付を足していた（OS=Apia で 2011-12-29 + 1 = 12-31）

## 10. R1 の残課題（P8-c1.1・2026-10-19）

§9 の残リスクのうち R1-P・R1-M はクライアントで修正した。R1-S は SQL の変更が要るので**実装せず、承認用の案**としてまとめた。
SQL・マイグレーション・本番 DB は変更していない（ローカルの隔離 DB で `SELECT` と、ROLLBACK するトランザクションだけを実行）。

### 10.1 R1-P: 空き枠クリックの初期値

**クリックの意味。** 週・日表示の時刻グリッドは「壁時計の 24 時間 × 30 分刻み」の軸で、月表示のセルとスマホの「この日に予定を追加」は
「その日付の 09:00」。どちらも**ある日付の壁時計**を指していて、瞬間を指してはいない。グリッドは2回ある時刻も1行に重ねて描くので、
クリックからはどちらの瞬間かを区別できない。

**修正前（実測、`instantFromZonedDayMinutes` = `fromZonedTime`）**

| クリック | 修正前の初期値 |
| --- | --- |
| Havana 3/8 00:00・00:30（0時台が存在しない） | **3/7 23:00・23:30**（前日。報告どおり） |
| New York 3/8 02:30（日中の存在しない時刻） | 01:30（黙って1時間前） |
| 2回ある時刻（NY 11/1 01:30・Havana 11/1 00:30） | OS のゾーン次第でどちらか。その選択がフォームに黙って入る |
| Apia 2011-12-30（日付ごと存在しない） | 12/29 09:00 |
| **どの地域でも** 23:30 の枠 | 終了の「24:30」が**同じ日の 00:30** になり、終了が開始より前（今回見つけた） |

**規則（`src/features/calendar/createTimes.ts` の `createTimesAt`）**

| クリックした壁時計 | 初期値 |
| --- | --- |
| 1つの瞬間を指す | その瞬間（修正前と同じ） |
| 存在せず、**その日付にそれより前の時刻が無い**（日付の始まりが遅れている。Havana 3/8 は 01:00 から） | その日付の最初の瞬間（01:00）。上の行が意味しうるのは「この日の始まり」だけで、前日は別の日付 |
| 日中に存在しない（NY 3/8 02:30） | クリックした時刻のまま。フォームの既存の説明（P8-b5.6b-2）が出て、変えるまで保存できない |
| 2回ある | クリックした時刻のまま。フォームがどちらかを聞く（未選択では保存できない） |
| 日付ごと存在しない（Apia 2011-12-30） | 日付を変えず、日中と同じ扱い |

終了は「開始が決まったら開始＋経過1時間」（壁時計＋1時間だと DST の日に存在しない時刻や2回ある時刻に当たり、23:30 の枠では同じ日の
00:30 になっていた）。開始を利用者に任せる場合は壁時計＋1時間を同じ規則で判定する。終了が2回ある時刻に当たり、どちらの瞬間かが
分かっている場合（NY 11/1 00:30 から1時間後 = 1回目の 01:30）は、その選択をフォームに渡す。

ダイアログは作成時に瞬間ではなく `{ local, at }`（壁時計と、決まっていればその瞬間）を受け取る。フォームの日付欄は常にクリックした日付。
通常の日は、2026-01-15・06-15 の全 48 枠 × 4 ゾーンで開始が修正前と完全に一致することをテストで確認した。

### 10.2 R1-M: 月表示の重複セル

**原因。** セルを OS ローカルの `new Date(y, m, d)` で作り、そこから日付を読み戻していた。OS が Pacific/Apia だと 2011-12-30 の
ローカル 0 時は存在せず、JavaScript は 12-31 0:00 に進めるので、12 月に「31」が2つ（キーも重複）、30 日が無かった。
同じ原因で 2012 年 1 月の表示（前月末の行）も同様だった。

**修正。** 日付を UTC の暦計算（ゾーンに依存しない）で求め、そこから `dayKey` と表示用の `dayOfMonth` を作る。`date` は従来どおり
その日のローカルの最初の瞬間（読み戻しには使わない）。月表示・コンパクト月の数字は `dayOfMonth` を表示し、`monthGridRange` も
日付キーから範囲を作る。日付が飛んだ日は「長さ0の日」として 1 マス表示される（週表示ともともと同じ）。

月曜始まり・前後の月にまたがる行・今日の印・予定の位置（`dayKey` ベースのまま）・通常の日本時間の表示（2026 年 8 月 = 7/27〜9/6）は
変化なし。6 OS ゾーン × 10 か月でテスト。

**残る制約。** 表示の基準が「瞬間（Date）」なので、Apia で 12/30 を**選択**すると 12/31 になる（その日付には瞬間が無い）。
2011 年の 1 日だけで、直すには表示状態の持ち方を変える必要があるので記録のみ。

### 10.3 R1-S: 2回ある深夜0時（サーバーとクライアントの不一致）の監査

#### 修正案

**案1（推奨）: SQL をクライアントに合わせる（最小変更・1回目の深夜）**

新しい補助関数を作り、0025 の3か所の式だけを置き換える（`free_busy_available` の本体を `create or replace` で再定義。差分は3行）:

```sql
-- 0027（案）。暦日 d がゾーン tz で始まる瞬間 = tz での日付が d 以降になる最初の瞬間。
-- PostgreSQL は2回ある壁時計を「後」に解決するので、一つ前のオフセットで読んだ候補が
-- 本当に d の 0:00 を指し、しかも早いなら、それが1回目の深夜。
create function timeweave_private.zoned_day_start(p_d date, p_tz text)
returns timestamptz
language sql
stable
strict
set search_path = ''
as $$
  select case
           when e.cand < l.later
            and (e.cand at time zone p_tz) = p_d::timestamp
           then e.cand
           else l.later
         end
  from (select (p_d::timestamp at time zone p_tz) as later) as l,
       lateral (select ((p_d::timestamp
```

### 11.1 根本原因（再掲）

0025 の `free_busy_available` は、終日の日付を所有者ゾーンの瞬間に `d::timestamp at time zone tz` で変換していた（§6b・§6c・§7B の3か所）。
深夜 0:00 が2回ある日、PostgreSQL は**後（2回目）**を選ぶ。クライアント（§9）と JavaScript の Date は**1回目**。
そのため「最初の 0 時台」がサーバーでは前日、画面では当日になり、S1〜S4 が起きていた。0025 の 6b のコメントにあった
「どちらを選んでも同じ暦日を指すので受け入れる」という前提が誤りだった（暦日は同じでも、境界の位置が1時間違う）。

### 12.1 既存の規則（どこで決まっているか）

**単発予定の確定（P8-b5.6b-2）と、繰り返しの各回の解決は別の規則。** 単発はフォームで利用者が決める（存在しない時刻は保存拒否、
2回ある時刻は選択）。繰り返しの各回は、DTSTART の壁時計をその日付に置いて**自動で**瞬間にする。

| 対象 | 実装 | 存在しない時刻 | 2回ある時刻 |
| --- | --- | --- | --- |
| 時刻つき・ゾーンあり（M1、5b-4 以降の通常） | クライアント `expandRule` → `resolveZonedWallClock`（`src/utils/timezone.ts`）／SQL `rrule_timed_occurrence_starts_in_zones`（0018）の `v_cl at time zone p_timezone` | **後の候補** ＝ 時計の進み分だけ後ろへ（02:30 → 03:30） | **後（2回目）** |
| 時刻つき・ゾーンなし（M0、旧データ） | クライアントだけ（OS ローカルの `new Date(y,m,d,h,mi)`）。SQL は展開せず Busy を `complete=false` にする | 後ろへ（JS の規則） | **前（1回目）**（JS の規則） |
| DTSTART 自身 | 保存した瞬間をそのまま使う（再解決しない、両側とも） | — | 作成時に選んだ側を保つ |
| 終日 | 日付の計算（両側）。瞬間化はクライアントの OS ローカル 0 時 | — | — |
| 期間 | 終了 ＝ 開始 ＋ マスターの経過時間（両側） | 終了も一緒に動く | 同左 |

「後の瞬間」は PostgreSQL の `AT TIME ZONE` の規則で、クライアントはそれに合わせている（`resolveZonedWallClock` のコメント）。
暦日の境界（§9・§11 の `dayStartInstantIso`／`zoned_day_start`、**1回目**の深夜）とは別の問いで、両者が違う側を取ることは
矛盾ではない（「日の始まり」と「その時刻に置かれた予定」）。

### 12.5 共有 Busy/Available への影響（`supabase/tests/P8c2_recurrence_dst_test.sql`、18 行、両 DB で全件 ok・出力同一）

- 秋の二重時刻: Busy は 2回目の 01:30 だけ。重なる Available はその 30 分だけ削られる（1回目の 01:30 は Busy ではないので空きとして出る ―
  所有者のカレンダーの表示と同じ）
- 春の欠落: Busy は 03:30 EDT。Available はそこだけ削られる
- 例外: その回の削除で Busy が消える／移動で移動先だけ Busy／**置けない slot（もう一方の 01:30）は Busy が INCOMPLETE・Available は indeterminate**
- `include_private`: private の繰り返し Busy は ON で効き、OFF では共有されない（既存の契約）。busy_only は OFF でも Busy として効く
- Available 型の繰り返しも同じ規則で展開され、Busy に削られる（Busy 優先）
- 深夜の切替（Havana・Azores）・Nuuk・Tokyo・終日の繰り返し（所有者ゾーンの 0 時で時刻 Available を切る）も期待どおり
- 詳細（タイトル等）を返さないことと RPC の形は 0027 のスイートで確認済み（§11.6）。このスイートは Busy/Available の値だけを見る

**Busy の欠けによる過剰開示は見つからなかった。** クライアントとサーバーの発生回が同一で、食い違う例外は fail-closed になるため。

### 13.3 見つけた問題と修正

**問題（修正済み）**: 存在しない時刻を入力すると、`new Date()` がそれを**後ろの瞬間**にしていた。入力した文字の

### 15.5 推奨

**案A（現行を正式に維持）。** 理由:

1. 現行の契約はすでに一貫しており、公開ガイドとも一致し、保存・再編集・共有・DST のすべてで瞬間が保たれることを実証した（6,912 件、0 件の不一致）
2. 案B の効果は「別地域の時刻を暗算しなくてよい」ことに限られ、そのために DB の制約・トリガー・型・UI・往復規則を作り直す必要がある。
   TimeWeave の主目的（自分の予定と、その Busy/Available を共有すること）は瞬間で完結しており、共有にも利益が無い
3. 案C は「入れた地域が後で分からない」ため、開き直したときに誤解を招く。採るなら案B まで進むべきで、中間案としての価値が低い
4. 将来必要になったら、案B は「既存はゾーン NULL＝ブラウザのゾーン」として後方互換に追加できる。今決めなくても失うものが無い

案A を採る場合の追加作業（任意・小）: ガイドの「タイムゾーン」章に「別の地域の時刻で予定を入れるには、その時刻を自分の端末の時刻に
直して入力する（例: 東京からニューヨーク 9:00 → 23:00）」の一文を加える。今回は仕様が未確定なのでガイドは変更していない。

### 17.2 展開できない繰り返し（K12）

クライアントが展開できない規則（`FREQ=YEARLY`・COUNT と UNTIL の併用・不正な区切り・`BYDAY=XX`・`INTERVAL=0`・FREQ なし、
または展開器が受け付けないゾーン）を持つマスターは、**そのシリーズ全体（マスターと、それを指す例外すべて）をカレンダーに描かず**、
件数を所有者に知らせる。他の行の展開は1バイトも変わらない（`src/services/occurrencesMalformed.test.ts`）。

- 対応する規則は増やしていない（上の規則はすべて引き続き拒否される）。発生回・例外キー・DST の規則は不変
- 共有は無関係: Busy/Available は SQL が行から直接計算し、同じ行に対して Busy `complete=false`・Available indeterminate を返す
  （`supabase/tests/P8f3a_malformed_rrule_share_test.sql`、0027 未適用・適用済みの両 DB で 25 行すべて ok）
- 例外を単独で描かない理由: 例外を開くとダイアログがマスターの規則をフォームに読み込み（`parseRRule`）、そこで同じ例外が出る
