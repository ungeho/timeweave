## 1. 現状の事実

### 使用箇所

| 場所 | 型 | 必須か |
| --- | --- | --- |
| `EventDialog.tsx:558,566` | `datetime-local` ×2（開始・終了） | **必須** |
| `EventDialog.tsx:542,547` | `date` ×2（終日の開始日・終了日） | **必須** |

### 問題の正体

**`required` 属性が付いていない。** `EventDialog.tsx` 全体で `required` の出現は
1回のみで、日時入力には付いていない。

このため、Chrome の日時ピッカーが出す**クリア操作（✕ / 「削除」）が有効**になり、
必須の日時を空欄にできてしまう。空欄のまま保存すると、はじめて
`event.error.dateRequired`（"Please enter a date" / 「日付を入力してください」）が
出る。

つまり **「消せるのに、消すと必ず怒られる」** 操作が存在している。

### 既存の依存関係

```
dependencies: @supabase/supabase-js, date-fns, date-fns-tz, react, react-dom
devDependencies: @types/react, @types/react-dom, @vitejs/plugin-react,
                 markdown-it, typescript, vite, vitest
```

UIライブラリは**ゼロ**。CSSフレームワークも無く、`src/styles/global.css` の
手書き1本。jsdom も入れない方針で、vitest は `environment: 'node'`。

この構成は偶然ではなく、プロジェクト全体の方針として保たれている。

## 3. 推奨

### **案1 を採用する。** `required` を付けて標準UIを維持する。

理由:

1. **報告された課題がこれで消える。** 「必須なのにクリアできる」は `required` の
   欠落そのものであり、ピッカーの実装方式の問題ではない
2. **依存0・jsdom不要**で、プロジェクトの既存方針（UIライブラリ無し・node環境での
   純関数テスト）と矛盾しない
3. **アクセシビリティとスマホ操作性は標準実装が最良**。案2〜4はいずれも標準を
   下回るリスクがある
4. タイムゾーン変換は `utils/datetime.ts` と `date-fns-tz` に閉じており、**ここに
   手を入れないのが最も安全**。P7で検証した終日/繰り返し/共有の挙動に波及しない

### 併せて行う補強（P8-b で実施）

| # | 内容 |
| --- | --- |
| A1 | 必須の4つ（開始・終了・開始日・終了日）に `required` |
| A2 | 繰り返しの終了日は `endMode === 'until'` のときだけ `required` |
| A3 | **`ShareDialog` の有効期限は任意なので `required` を付けない**（クリアできてよい） |
| A4 | 入力高さを44pxに（モバイル） |
| A5 | 既存の検証（`event.error.dateRequired` 等）は**残す**。`required` はブラウザの事前防御であり、保存時の検証を置き換えない |

### 採用しない場合の再検討条件

以下が発生したら案3を再評価する。

- 開始/終了の相互制約をUI上で表現する要求が出た（例: 終了は開始以降しか選べない）
- デザイン統一の要求で標準UIの見た目が許容できなくなった
- iOS Safari の `datetime-local` に実機で致命的な問題が見つかった（未検証）

### P3 の確認結果: `required` は検証を増やさない

`EventDialog.tsx` に **`<form>` 要素は存在しない**（`<form` と `onSubmit` の
出現は0件）。保存はボタンの `onClick={handleSave}` で起動している。ファイル内の
`required` という文字列1件も、HTML属性ではなく i18n キー
`event.title.required` である。

したがって `required` を付けても:

- **ブラウザのHTML検証は走らない**（送信イベントが無いため）
- 効くのは**ネイティブピッカーのクリア操作が消えること**だけ

これは今回の課題——「必須なのに消せる」——を解決するのに十分だが、
**「required を付けたから検証される」と誤解しないこと。** 保存時の
`event.error.dateRequired` 等のJS検証が引き続き唯一の防御であり、A5 のとおり
残す。

なお、`required` でクリアボタンが実際に消えるか自体は実ブラウザで未確認
（P1）。消えなければ、`<input>` を直接置き換えずに「空になったら直前の値へ
戻す」`onChange` ガードで代替できる（依存0・数行）。

# P8-b5 実測と再評価（2026-10-18）

## 1. P8-a の推測は外れていた

本資料の旧記述:

> `required` が付くと Chrome はクリアボタンを**出さなくなる**

**これは誤りだった。** Windows Chrome 155 で最小構成を並べて実測した結果:

| | インラインのクリアボタン | Delete 1回で空にできるか | `valueMissing` |
| --- | --- | --- | --- |
| `datetime-local`（現行） | **元から無い** | **できる**（`value` が `''` に） | false |
| `datetime-local` + `required` | **元から無い** | **できる**（変化なし） | **true** |
| `date` / `date` + `required` | 同上 | 同上 | 同上 |

`required` が変えるのは**バリデーティ状態だけ**で、クリア操作そのものは防がない。
`:invalid` が当たるようになるので、CSSで印を付けられる——それが得られるすべて。

ネイティブのドロップダウン内にクリア項目があるかは、**OSレベルのポップアップで
タブ撮影に写らないため未検証**。ただし下記のとおり、それは主要な問題ではなかった。

## 2. 本当の不具合はクリアボタンではなかった

時刻指定の開始日時を空にして保存を押すと:

- ダイアログは開いたまま
- **エラーメッセージが出ない**
- コンソールに `Invalid datetime-local value:` の**未処理の例外**

原因は2つ:

1. **終日分岐には空チェックがあり、時刻指定分岐には無かった。**
   `isoFromDatetimeLocalValue('')` は throw する
2. **`handleSave` が `buildSaveResult()` を try の外で呼んでいた。**
   throw が未処理のまま抜け、画面上は「保存ボタンが無反応」になる

つまり報告された「空欄にできてしまう」の実害は、空欄にできること自体ではなく
**空欄のまま保存を押すと沈黙すること**だった。

## 3. 採用した修正

| # | 内容 |
| --- | --- |
| 1 | 時刻指定分岐に空チェックを追加 → `event.error.dateRequired`（既訳あり） |
| 2 | `buildSaveResult()` を try の中へ。取りこぼしもメッセージになる |
| 3 | 必須の4入力＋繰り返しの終了日に `required`（**クリア防止ではなく `:invalid` の印のため**） |
| 4 | `:invalid` の枠線を赤に（PC・スマホ両方） |
| 5 | **共有リンクの有効期限には付けない**（任意項目。付けると期限を消せなくなる） |

禁止ではなく検証メッセージで扱う方針。直前の値へ戻す実装は**採用しなかった**
（直接入力・部分編集・入力途中状態を壊すため）。

## 4. MUI X DateTimePicker の評価（2026-10-18 調査）

### 結論: **採用しない。** 決定的な障害がある。

### 4.1 タイムゾーン非対応（決定的）

MUI X 公式ドキュメント:

> Only `AdapterDayjs`, `AdapterLuxon` and `AdapterMoment` are currently
> compatible with UTC dates and timezones.

**`AdapterDateFns` はタイムゾーンに対応していない。** 本アプリは date-fns +
date-fns-tz で、オーナーのタイムゾーン・DST・タイムゾーン付き繰り返し
（0024 の Available 判定を含む）が中核にある。選択肢は2つしかない:

- **(a) `AdapterDateFns` のまま** → ピッカーがタイムゾーンを理解しない。
  本アプリで最も壊してはいけない部分を、理解しない部品に渡すことになる
- **(b) Luxon か Day.js を追加** → date-fns / date-fns-tz と**意味論の異なる
  日付ライブラリが2系統**同居する。境界で変換が必要になり、DSTのバグは
  まさにそこで生まれる

### 4.2 依存の追加コスト

`package.json` の実測: **Material UI は未採用**。deps は 5 つだけ
（`@supabase/supabase-js`, `date-fns`, `date-fns-tz`, `react`, `react-dom`）。

| 追加物 | 概算 (gzip) |
| --- | --- |
| `@mui/material`（`@mui/x-date-pickers` の peer） | 約 136 KB |
| `@emotion/react` + `@emotion/styled` | 約 12〜15 KB |
| `@mui/x-date-pickers` | 別途 |
| Luxon または Day.js + プラグイン（4.1(b)の場合） | 3〜20 KB |

**現在のバンドル実測: JS 192,897 B + CSS 5,984 B = gzip 約 199 KB。**
入力欄2つのために**ほぼ倍**になる。加えてテーマシステムが入る
（本アプリは UIライブラリ依存ゼロで作られている）。

ライセンスは Community が MIT で DateTimePicker を含む。有償は範囲選択のみ。
**ライセンスは障害ではない。**

### 4.3 UX面で実際に得られるもの

| 要望 | MUI X | ネイティブの現状 |
| --- | --- | --- |
| PCのキーボード直接入力 | `TimeField` で可能 | **既に可能**（セグメント単位の入力・矢印キー） |
| スマホのGUI操作 | `MobileTimePicker` | **OS標準**（Android=マテリアルのアナログ時計、iOS=ホイール） |
| アナログ時計 | `TimeClock`（`viewRenderers` で desktop にも） | **Android は標準がアナログ時計** |
| 日付と時刻の相互編集 | 可能 | 可能 |
| 24時間表記 | `ampm` / `format` で**言語ごとに指定が必要** | **ブラウザのロケール依存**（下記） |

要望の中心である「スマホのGUI」は、**Android では OS 標準がすでに
マテリアルのアナログ時計**であり、MUI を入れると OS 標準を自前の実装で
置き換えることになる。PCのキーボード入力も標準で既に実用的。

### 4.4 ただし一つだけ、標準では解決しない問題がある

**ネイティブ入力の表示形式はブラウザのロケールに従い、アプリの言語設定に
従わない。** 本アプリは表示側で `CLOCK_24H`（`hourCycle: 'h23'`）を使って
24時間表記に統一しているが、**入力欄だけはその統一から外れる**。
英語ロケールのブラウザでは入力欄が AM/PM になり、画面上の他の時刻表示と
食い違う。

これは実在の不整合で、ライブラリ導入が解決する唯一の項目。
ただし**これだけのために 199 KB → 約 400 KB は見合わない**と判断する。

入力UXをさらに改善するなら、依存を増やさない以下を提案する

# P8-b5.6a 追記（2026-10-19）: 4.1 の「決定的」は修正する

試作（`prototypes/datetime-picker/`、詳細は `docs/p8-datetime-picker-prototype.md`）で
MUI X を実際に動かした結果、**4.1 のタイムゾーン非対応は、この境界では障害に
ならない**ことが分かった。

- 部品には TZ を渡さず、`"YYYY-MM-DDTHH:mm"` の壁時計の値だけを編集させる。
  ISO 化は従来どおり `utils/datetime.ts` が保存時に行う
- この構成で `AdapterDateFns` は本体と同じ date-fns 3 のまま動き、**第2の日付
  ライブラリは不要**だった
- MUI X の TZ 機能（Day.js/Luxon/Moment 限定）と、TimeWeave への統合可能性は
  別の問題。後者は「壁時計として使う限り可能」

残る論点はサイズ（実測 +約 136〜141 KB gzip、本体 193 KB の約 +70%）、
CSS-in-JS の同居、**ピッカー操作中も `onChange` が出る**こと（`onAccept` で確定する
設計が要る）、DST のある TZ で存在しない時刻が入力中に書き換わる可能性（未検証）。

§6 の「MUI X の実機操作性（試作は作っていない）」は解消。操作できる試作を用意した。
