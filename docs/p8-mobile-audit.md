スマホUX改善の着手前調査。実装は行っていない（§6 の1件を除き、それも提案に留める）。

## 1. 調査方法

iframe を使って**実際のCSSビューポート**を変更した。iframe は自身の幅でメディア
クエリを評価するため、ウィンドウを操作できない環境でも発火させられる。依存関係は
追加していない。

- アプリは `vite build --mode mockapi` でビルドし、`scripts/mock-supabase.mjs`
  （127.0.0.1 限定）の架空データに対して動かした
- 幅: 320 / 360 / 375 / 414 / 768 / 1280px
- 本番Supabaseへは接続していない

測定したのは見た目ではなく**数値**である。`documentElement.scrollWidth`、要素の
`getBoundingClientRect()`、タップ対象の寸法、モーダルの内部スクロール量。

## 2. もっとも重要な発見

### B1. 横スクロールが発生する（320 / 360 / 375px）— Blocker

`scrollWidth` が **387px** で固定される。原因を切り分けた結果、
**ヘッダーのメールアドレス1要素**だけが原因だった。

| 幅 | 通常 | ヘッダー操作部を隠す | **メールだけ隠す** |
| --- | --- | --- | --- |
| 320px | 387 | 320 | **320** |
| 360px | 387 | 360 | **360** |
| 375px | 387 | 375 | **375** |

`.app-header-actions` は幅276pxで、右端が388px。内訳はメール(87px)＋設定＋
ログアウト＋テーマ切替。`.app-header` は `justify-content: space-between` の
flex だが、子に縮小の余地が無いため、はみ出した分がページごと横に伸びる。

414px以上では発生しない。

**最小の修正**（P8-b で適用）:

```css
@media (max-width: 480px) {
  .user-email { display: none; }   /* 設定ダイアログに出ているので情報は失われない */
}
```

ただし P8-b でヘッダー自体を再設計するなら、そこに吸収してよい。

### B2. カレンダーのチップが1文字に潰れる（320〜414px）— Blocker

月表示は7列固定。セル幅は **320px:41 / 360px:46 / 375px:49 / 414px:54**。
チップのタイトルが `定`・`レ`・`面`・`相` の1文字まで削られ、**何の予定か読めない**。

既存の `COMPACT_MONTH_QUERY`（640px）はチップ上限を3→2に減らすだけで、幅の問題は
扱っていない。週表示も同じ7列で、列幅47px。

これは縮小では解けない。**画面構成の変更が要る**（設計は `p8-mobile-design.md`）。

### B3. ツールバーが3段に折り返す（320〜414px）— Important

高さ **76〜90px**（768px以上では33px）。「今日 ‹ › 2026年10月」「月 週 日」「共有」
が別々の行になる。320pxでは月タイトルが「2026年10」「月」と2行に割れる。

ヘッダー(67px)と合わせて**上部だけで143〜157px**、720px高の画面の約2割を消費する。

### B4. タップ対象が小さい — Important

| 幅 | 44px未満の対象 |
| --- | --- |
| 320px | 16 |
| 360〜414px | 17 |
| 768px以上 | 19 |

代表例: `‹` `›` が **27×33px**、`月`/`週`/`日` が 42×31px、テーマ切替が 48×31px。
予定ダイアログでは **9入力中8つが高さ44px未満**（約34px）。

## 5. 未検証事項

| # | 項目 | 理由 |
| --- | --- | --- |
| U1 | **実機のタッチ操作** | iframe はCSSビューポートを変えるだけ。タップ精度・スワイプ・慣性スクロールは再現しない |
| U2 | **ソフトキーボード表示時の挙動** | `.modal { max-height: 90vh }` は**レイアウトビューポート**基準。実機でキーボードが出ると visualViewport が縮み、モーダル下部（保存ボタン）がキーボードの裏に入る可能性が高い。要実機確認 |
| U3 | `:focus-visible` の表示 | ウィンドウが背面だと `:focus` が成立しない（P7 と同じ制約） |
| U4 | iOS Safari 固有の挙動 | `datetime-local` のホイールUI、`100vh` の扱い、セーフエリア |
| U5 | ログイン画面のモバイル表示 | 認証フローを通していない |
| U6 | 画面回転（横向き） | 未測定 |

U2 は設計上もっとも影響が大きい。P8-b で `visualViewport` API を使うかどうかの
判断材料になるため、**実機確認を最優先の未検証事項**として扱う。
