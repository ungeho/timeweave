## 3. K6: 0027 の重点監査

### 3.1 本番に適用していない場合の具体的なリスク

本番の `free_busy_available`（0025、2026-10-11 本番適用）は、深夜0時が2回ある日の終日の境界を**2回目**の深夜にする。
隔離 DB の実 RPC（anon）で再現した内容（§11.5【実測】）:

| # | 内容 | 種類 |
| --- | --- | --- |
| S1 | 終日 Busy の日の最初の1時間に、時刻つき Available が出る | **Busy 優先の破れ（過剰開示）** |
| S3 | 終日 Available の前日の断片が、当日の最初の1時間まで延びる | **宣言していない1時間の開示** |
| S2 | 前日の終日 Busy に、当日1回目の 0 時台の宣言済み Available が隠れる | 過少開示 |
| S4 | 当日の終日 Available が、1回目の 0 時台の時刻つき Busy に削られない | 過剰開示 |

**発生条件（すべて満たすとき）**: 所有者が設定でタイムゾーンを宣言している ∧ そのゾーンに深夜0時が2回ある日がある
（現役は America/Havana・Atlantic/Azores）∧ 共有の期間がその日にかかる ∧ その期間に終日の予定と時刻つきの予定が両方ある
∧ リンクが `share_available=ON`（S1・S3・S4 の過剰開示は Available の公開が前提）。

## 4. K7: 繰り返し DST の現行仕様と D1〜D4

### 4.1 現行仕様（P8-c2 §12【実測】）

| 事項 | 規則 |
| --- | --- |
| 存在しない時刻（ゾーンありの繰り返し M1） | 時計が進む分だけ**後ろへ**（NY 02:30 → 03:30 EDT）。回は作られ、エラーにも欠落にもならない |
| 2回ある時刻（M1） | **2回目**（NY 01:30 → 01:30 EST）。両方は作らない |
| 日付をまたぐ欠落（Nuuk 型） | 土曜 23:30 の回が**日曜 00:30** に移る（曜日が変わる。2026-03-28 などに実在） |
| M0（ゾーンなし） | 2回ある時刻は**1回目**（JS の規則）。共有では展開しない（fail-closed） |
| DTSTART 自身 | 保存した瞬間をそのまま（作成時に選んだ側） |
| クライアントと SQL | 10 ゾーン・2024〜2027 年の全切替・**8,088 シリーズで発生回が完全一致**（0027 の有無に関係なく）。OS ゾーン 6 種で同一 |
| 例外 | 生成した瞬間を slot に持つので、規則を変えない限り同じ回を指す。食い違う slot は SQL が `complete=false`（fail-closed） |

「日の始まり」（0027・終日の境界）は**1回目**の深夜、「その時刻の予定」は**2回目**。問いが別なので矛盾ではない（§12.1）。

### 4.2 D1〜D4（原資料 §12.7 の再確認）と推奨

| # | 事項 | 現状 | 推奨 | 理由 |
| --- | --- | --- | --- | --- |
| D1 | 2回ある時刻の回をどちらにするか | 2回目（M1）。M0 だけ1回目 | **現状維持** | PostgreSQL の `AT TIME ZONE` と同じ規則で、共有の SQL と一致済み。変えると既存の例外キーの移行と SQL の変更が要る |
| D2 | 存在しない時刻が日付をまたぐ場合（Nuuk 型） | 翌日 0:xx に移り曜日が変わる | **現状維持＋ガイドに明記** | 他の選択（前日に寄せる・作らない）はクライアントと SQL の両方と、該当回の例外キーの扱いが必要。影響は該当地域で年1回 |
| D3 | M0 の旧シリーズ | 1回目・共有では展開しない | **現状維持** | fail-closed。利用者がダイアログからゾーンを付けられる。一括移行は本番データの更新で別の承認事項 |
| D4 | 作成・編集時の案内 | 将来の回が DST に当たることは伝えない | **将来対応** | 新しい UI（新機能）。完成の条件にはしない |

**現行仕様を維持する利点**: 追加の実装・移行・本番 SQL の変更が無い。クライアント・サーバー・既存の例外が一致したまま。テストで固定済み
（`recurrenceDst.test.ts` 70 件、`P8c2_recurrence_dst_test.sql` 18 行）。

**残る制限**: 年1回、DST のある地域で 02:30 の回が 03:30 に、01:30 の回が2回目になる。Nuuk 型の地域では曜日が変わる回がある。
これらは「この回だけ編集」で手で直せる（既存機能、§12.6 案C【実測】）。

**ガイドとの関係**: ガイド「タイムゾーン」章の「夏時間の切り替えと時刻の入力」は、**1回の予定の入力**（存在しない時刻は保存できない、
2回ある時刻は選ぶ）だけを説明しており、**繰り返しの回が自動で補正されること**は書かれていない【確認】。案A を採るなら、
「繰り返し予定」章に数行の説明を足すのが完成の条件（§7）。

- **確認（クライアント）**: UTC・東京・New York・Kiritimati（+14）・Pago Pago（−11）・Apia・Havana の 7 ゾーンで、9999-12-30 はその日の終わりの瞬間（例 `UNTIL=99991231T105959Z`）として保存・読み戻し・展開でき、9999-12-31 は拒否される
- **確認（SQL・隔離 DB）**: 上の UNTIL はすべて `rrule_parse` で ok。時刻つき・終日の文法ゲートもクライアントと同じ側に振り分け、9999 年 12 月の展開も動く。`UNTIL=100000101T000000Z` は SQL でも malformed

| **REST API への直接書き込み（所有者自身のトークン）** | **DB だけ: 長さ 255 バイトのみ。形式は検証されない（K16）** | RLS で自分の行に限る | **255 バイト以下なら何でも** | なし（保存される） |

| 匿名（anon） | — | `events` への権限なし。実行できるのは `get_free_busy`（SECURITY DEFINER）だけ | 不可 | 権限エラー |
| RPC 経由の操作 | 予定を書く RPC は存在しない（共有リンクの RPC のみ） | — | — | — |
| 既存データの読み込み（クライアント） | `parseRRule`（読み取りは寛容なまま。K13・K14 で狭めていない） | 所有者 | — | 読めないものは K12 でシリーズごと隔離 |
| 共有（匿名の閲覧） | SQL の `rrule_parse` と文法ゲート | トークン・期限・失効 | — | 読めない・展開できない規則は Busy `complete=false`・Available indeterminate |
| 例外行とマスター | CHECK（例外は rrule を持てない、slot の型）、複合 FK（同じ所有者・CASCADE）、0017 のグラフ制約 | RLS | — | 不一致の slot は SQL が fail-closed |

**RLS は「他人が書けない」ことを保証するが、「所有者が不正な規則を保存できない」ことは保証しない。** 後者を閉じるのが K16。

### 12.5 K15: タイムゾーン名の検証の負荷 — 修正案 0028 の評価

**正確な原因**: `timezone_is_supported`（0008）が `pg_timezone_names` を検索している。これは集合を返す関数で、呼ばれるたびにゾーンのディレクトリを走査し、
598 個のゾーンファイルを読み込んで解析する（呼び出しをまたぐキャッシュは無い）。`exists (...)` でも全行を作ってから探す。
隔離 DB（PostgreSQL 18.6・Windows）では 1 回の走査が 106 ms、`timezone_is_supported` 1 回が約 145 ms。`pg_timezone_abbrevs` は 0.35 ms。
0018 のヘッダーにも PostgreSQL 17.10（ローカル）で約 140 ms の記録がある。**本番（Linux）の値は未計測。**

**影響（隔離 DB の実測）**

| 経路 | 条件 | 実測 |
| --- | --- | --- |
| 書き込み・実経路（全トリガー有効） | 時刻つき繰り返し 150 行を 1 文で | **21.8〜22.0 秒**かけた後に 0012 が拒否する。拒否された文は消費を残さないので、**何度でも繰り返せる**（0012 自身が「リクエスト数の制限は edge の仕事」と明記） |
| 書き込み | 200 行 | 30.9 秒 |
| 匿名の共有 RPC | 所有者が 20 種類のゾーンを使う | 1 回 **5.95 秒**（core と helper で 2 回ずつ検査）。598 種類なら約 3 分になり、毎回タイムアウトまで CPU を使う |
| 匿名の共有 RPC・実経路 | ゾーン 1 種類 | 1 回約 150 ms。同じリンクでは 15 回で PT429（0019） |

本番では Supabase のロールごとの `statement_timeout`（未確認）で 1 リクエストの上限が切られる。それでも、**その時間いっぱいの CPU を、拒否されてもコストなしに繰り返し使わせられる**。

**代替方式の比較（隔離 DB）**

| 方式 | 結果の一致 | 速さ | 評価 |
| --- | --- | --- | --- |
| 現状 | — | 145 ms／回 | — |
| A1: 形の検査 ＋ `AT TIME ZONE` が通るか | **一致しない**: 略号 189 個（`CDT`・`ACST` など、固定オフセット）も受け付ける | 約 0.0015 ms／回 | 不採用（DST の意味が変わる） |
| A2: A1 ＋ 略号表で除外 | 略号でもあるゾーン名（`EST`・`UTC` など）の扱いを手で持つ必要がある | 速い | 不採用（壊れやすい） |
| 非公開スキーマの表にキャッシュ | 一致 | 速い | 可能。ただし表を読む権限のために SECURITY DEFINER が要り、更新忘れの問題は 0028 と同じ |
| **0028: 一覧を IMMUTABLE 関数に焼き込む** | **完全に一致**（598 名＋境界値 16 で差 0。適用時のゲートで一覧＝`pg_timezone_names` を強制） | 50,000 回で 4.3 ms | **条件付きで採用を推奨** |

**0028 の検証（隔離 DB のコピー）**:
- 既存の SQL 8 スイートの出力が適用前後で同一
- 書き込み 200 行: 30.9 s → 9.9 ms。20 ゾーンの匿名 RPC: 5,951 ms → 21 ms
- 誤ったロールでは中止される
- ロールバックで関数・権限の指紋が適用前と完全に一致し、2 回の再適用も成功（冪等）

**権限・所有者・search_path**:
- 新しい関数は `search_path = ''`・IMMUTABLE・STRICT で、中身はゾーン名の一覧（公開情報）だけ
- `public, anon, authenticated, service_role` から剥奪し、`authenticated` だけに付与する（`timezone_is_supported` と同じ。書き込みトリガーはログインユーザーとして動く）
- Supabase の既定権限（public に作った新しい関数へ anon などの EXECUTE を付ける）は、作成直後の REVOKE で打ち消す
- `timezone_is_supported` は CREATE OR REPLACE なので所有者・ACL を保つ。適用は `timezone_is_supported` の所有者で行う（ガードあり）
- 権限の拡大は無い

**PostgreSQL 17**: 使う機能（`format`、IMMUTABLE な SQL 関数、配列リテラル、`parallel safe`）はすべて 17 にある。**ただし 17 では実行していない**（ローカルは 18.6 のみ）。

**tzdata 更新の危険と運用負担（採用する場合に必ず受け入れるもの）**
- 一覧は適用時点で固定される。サーバーの tzdata が更新されて**新しいゾーンが追加されると、そのゾーンでの時刻つき繰り返しの保存が拒否される**（`TIMEWEAVE_TZ_INVALID`）。直すには一覧の再生成（0028 の §1 を再実行）が必要
- **削除・改名されたゾーン**は一覧に残る。ただし共有側の `timezone_is_resolvable`（`AT TIME ZONE` の検査）は変えていないので、解決できなければ fail-closed になる（漏えいはない）
- **運用**: Supabase の PostgreSQL・OS の更新のたびに、次の読み取り専用の確認で 0 であることを見る（0 でなければ再生成する）:
  `select count(*) from pg_timezone_names z where not public.timezone_name_listed(z.name);`
- 更新を忘れた場合の影響は「新しいゾーンの利用者が時刻つき繰り返しを保存できない」までで、過剰開示・データ破損はない

**推奨**: **本番で 1 回だけ読み取りの計測（§12.9 P7）をしてから採否を決める。** ただし匿名 RPC はゾーン数倍、書き込みは行数倍の費用なので、1 回あたり数 ms でも最悪は秒単位になる。
ログインが誰にでも開かれているなら、**公開前に 0028 を（運用手順込みで）入れることを推奨**する。

### 13.1 K18: クライアントの日付範囲を DB と一致させた — 実装完了

- **原因**: DB（0013）が保存する範囲は、終日が `start_date`・`end_date`（排他的）とも [0100-01-01, 10000-01-01)、時刻つきが `start_at`・`end_at` とも [0100-01-01Z, 10000-01-01Z)。
  一方フォームは、終日を 9999-12-31 まで（排他的終了日 10000-01-01）、時刻つきは壁時計で 9999-12-31 まで（New York の 22:00 は UTC で 10000-01-01）受け付けていた。
  Supabase では DB が汎用のエラーで拒否し、ローカルモードでは保存されてしまった（**修正前に実ブラウザで再現**: 終日 9999-12-31 がローカルに `endDate: 10000-01-01` で保存された）
- **経路の確認**: 日付を書く保存は、通常の予定・繰り返し・この回のみの編集のすべてが予定ダイアログの保存処理を通る（削除・キャンセル・タイムゾーン変更は日付を書かない）。そこで一か所で判定する
- **修正**: 新規 `src/features/event/eventDateBounds.ts`（DB と同じ数字。テストが 0013 のファイルを読んで一致を確かめる）。ダイアログの終日・時刻つきの各分岐で、保存する値（排他的終了日・UTC の瞬間）を判定し、
  「終日の予定は 9999年12月30日 までの日付にしてください」「この日時は保存できる範囲を超えています。協定世界時（UTC）で 9999年12月31日 のうちに終わる日時にしてください」（と英語）で止める。日時の意味は変えていない（保存する値の計算は同じ式のまま）
- **確認**: 実ブラウザ（ローカルモード・日英）14 項目 OK（終日 9999-12-31 拒否→同じダイアログで 9999-12-30 は保存、New York 9999-12-31 22:00 は拒否・東京の同じ時刻は保存、通常の保存、範囲外の既存行があっても画面が壊れない・既存行は不変）。
  隔離 DB（RLS・全トリガー有効、0025 状態と 0027 適用済み）で、クライアントが許す最後の値は保存され、許さない値は `events_allday_range`・`events_timed_range` で拒否されることを確認（`supabase/tests/P8f3b_date_bounds_test.sql`、8 項目）
- **K17 との関係**: 時刻つき繰り返しの終了日（UNTIL）は 9999-12-30 までで、その日の終わりは最も西のゾーンでも UTC で 9999-12-31 の 11 時前（DB の範囲内）
