## 0. 撮影の前提

### 撮影台は既にある

P6.6 で構築した隔離モック環境をそのまま使う。

```
scripts/mock-supabase.mjs     ループバック(127.0.0.1)のみのモックAPI
.env.mockapi                  アプリをそのモックへ向ける
.env.mock                     Supabase未接続のローカルモード
```

**起動と撮影の手順は `docs/p7-screenshot-procedure.md` にある。**
本書は「何を撮るか」、手順書は「どう撮るか」を扱う。

**実ユーザーのデータが写り込まないことを、運用ルールではなく構造で担保する。**
モックは本番に接続する経路を持たず、返すのは架空のシードデータだけである。

| 懸念 | 構造上の担保 |
| --- | --- |
| 実ユーザーの予定 | モックのシードデータのみ。本番DBへの経路が存在しない |
| メールアドレス | `demo@example.test`（`.test` は予約TLDで実在しない） |
| 共有トークン | `mock-token-*`。本物は取得できない |
| 本番通信 | 127.0.0.1 のみ。P6.6 で実測0件を確認済み |

### 撮影はスクリプト化する

`scripts/capture-docs-images.mjs`（P7-d で作成）が、モック起動 → 画面遷移 →
言語切替 → 領域撮影 を一括で行う。手作業で撮らない。理由は2つある。

1. **更新漏れの検出**が、再実行して差分を見るだけで済む
2. 架空データ以外が写り込む経路を、人の注意力に依存させない

### 注釈番号は画素に焼き込まない

番号のみを薄く重ね、**説明は本文側の表に置く**。焼き込むと言語ごとに注釈入り画像を
作り直すことになり、文言修正のたびに画像再生成が必要になる。本文側に置けば翻訳は
本文だけで済み、読み上げ・拡大・モバイル表示にもそのまま対応できる。

### 言語別画像が必要か

| 種別 | 判断 | 理由 |
| --- | --- | --- |
| スクリーンショット | **言語別に必要** | UI文言が画素に焼き込まれるため共用できない |
| 比較表 | **画像にしない** | Markdown の表のまま。検索・コピー・読み上げ・折返しが効く |
| 概念図 | 言語別のSVG | テキストが編集可能で差分が読める。本プロジェクトは既にインラインSVGを採用済み |

### manifest

```
content/images/manifest.json
  { "<画像ID>": { "route", "scenario", "lang": ["ja","en"],
                  "viewport", "capturedAt", "appCommit" } }
```

P7-d で、本文が参照する画像が manifest に存在するかを検査するテストを追加する。
画素比較の自動化はフォント差で誤検知しやすいため、まずは参照整合性と撮影コミットの
記録に留める。

画像について、ビルドを止める検査を4つ追加した。いずれも**追加した本人には

| 検査 | 止める間違い |
| --- | --- |
| alt 必須 | 書いた人には読めてしまう |

### モックに加えた変更

**`empty` の意味を直した。** 従来は busy も available も空で、画面には「共有されて
いる予定はありません」と「共有されている空き時間はありません」の2つが積まれていた。
これは別々の状態を1つに混ぜたもので、計画の「Busyのみ」とも一致しない。busy を残し
available だけ空にした。全部空の場合は `nothing_shared` として分離した。

**`busy_wins` を追加した。** 0024 は `v_avail_t - v_busy_t` でSQL側で差し引くため、
重なったままの組はそもそもクライアントへ届かない。モックが返すのは**実サーバが返す
のと同じ、分割済みの形**である。重なったままを送るほうが演出になる。

### UIについての発見（アプリは変更していない）

**共有ページは帯を種別ごとにまとめて描画し、時刻順には並べない。** `busy_wins` では
15:00–16:00（予定あり）が先頭に出て、14:00–15:00 と 16:00–17:00（空き時間）が続く。

## 5. P7-c で見つかった実装上の問題

### 5-1. 状態（availability）の選択肢 — 解決済み（2026-10-13）

**当初「P6の取りこぼし」と記録したが、これは誤りだった。** 未翻訳は
**文書化された意図的な決定**で、`eventUi.i18n.test.ts` と `appUi.i18n.test.ts` が
理由ごと固定していた。

> `Busy` と `Available` はこのアプリが日本語でも使う用語であり
> （共有ダイアログが 空き時間(Available) と書く）、辞書を通すと
> その対応を壊す翻訳を招く。

この懸念は妥当だった。一方で、日本語のフォームに英語が2語だけ並び、
どちらにも日本語の名前が無いという代償があった。

**P7-c補修で、両方を満たす形に解決した。**

| | 変更前 | 変更後 |
| --- | --- | --- |
| 日本語UI | `Busy` / `Available` | `予定あり (Busy)` / `空き時間 (Available)` |
| 英語UI | `Busy` / `Available` | `Busy` / `Available`（不変） |

かっこ内に用語を残すことで、共有ダイアログ・ガイド・SQL との対応が
翻訳の良し悪しに依存せず保たれる。英語にかっこを付けないのは、
`event.visibility.*` と違ってラベル自体が用語だからである
（あちらは enum `busy_only` とラベル "Busy only" が別物なので意味がある）。

保存値 `busy` / `available` は不変。

### 5-2. `busy_only` と `public` は共有リンクに対して同じ挙動

全 migration を通して `visibility` の比較は `<> 'private'` の**59箇所のみ**で、
`busy_only` は `0001_events.sql` の CHECK 制約にしか現れない。

つまり匿名閲覧者から見て、`予定ありのみ (busy_only)` と `公開 (public)` は
**区別できない**。どちらも「予定あり」として同じに開示され、タイトルはどちらでも出ない。

バグではない（README もこの3値を将来の意図表明として位置づけている）が、
**「公開」というラベルから利用者が余分な開示を想像する余地がある。**
ガイドでは「差が出るのは private かどうかだけ」と明記した。

UI ラベルに含まれる enum 値（`予定ありのみ (busy_only)` 等）がこの誤解を
緩和している面はある。
