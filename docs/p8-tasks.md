## 順序の根拠

ブリーフは「カレンダー閲覧UXを優先」とある。設計もそれに沿うが、**P8-b1 を
その前に置く**。理由は2つ。

1. **B1（横スクロール）は1行のCSSで直り、閲覧UXの作業と競合しない。**
   放置すると以降のすべての測定にノイズが乗る（`scrollWidth` が常に387になる）
2. **ブレークポイントと `useIsMobile` は全タスクの土台**で、先に決めないと
   後続が各自で分岐を書き始める

日時ピッカー（P8-b5）は閲覧UXと独立しているので、並行でも後でもよい。

```
P8-b1 土台 ──┬─→ P8-b2 閲覧UX ──→ P8-b3 予定シート ──→ P8-b4 共有・設定
             │

                                                      └─→ P8-b6 ガイド更新
```

## P8-b3: 予定シート — **完了（2026-10-18）**

### 構成

720px未満は `.modal` ではなく `.sheet`（全画面）。ヘッダー／本文／フッターの3枠で、
**スクロールするのは本文だけ**。

| 枠 | 中身 | 高さ |
| --- | --- | --- |
| `.sheet-header` | キャンセル・見出し・保存 | 固定（`position: sticky`併用） |
| `.sheet-body` | 全入力欄＋エラー | 可変・`overflow-y: auto` |
| `.sheet-footer` | 削除（編集時のみ） | 固定 |

**フィールドは1本の `fields` 変数**で、PCモーダルとシートが同じものを描画する。
2つ目のコピーを作ると検証・選択肢・ラベルの置き忘れが片側だけで起きるため。
ライブリサイズで**同一コンポーネントのまま**入れ替わるので、編集中の内容が消えない
（720→360→720 で題名と終日の状態が保持されることを実測）。

### 実測（モックAPI・iframe）

| 幅 | 形 | 横スクロール | はみ出し | 44px未満 |
| --- | --- | --- | --- | --- |
| 320 / 360 / 375 / 414 / 719px | **シート** | なし | 0 | **0**（新規9・編集20コントロール） |
| 720 / 768 / 1280px | **モーダル（PC不変）** | なし | 0 | PC据え置き |

- 60文字の題名・英語UIでも横スクロールなし
- 空題名で保存 → エラーが本文内に表示され、**画面内に収まる**（`role="alert"`）
- Escape で閉じ、`body` のスクロールロックが**元の値に復元**される
- 繰り返し予定の編集で「この回のみ／すべての回」、繰り返し設定、削除すべて到達可能

### ソフトキーボード

`height: 100dvh`。`100vh` はアドレスバー格納時の高さで、表示中は画面より高くなり
ヘッダーが流れる。

**Android Chrome 相当として、ビューポートを 640→380px に縮めて実測**:
シートが380pxへ追従し、ヘッダーと保存ボタンは画面内、本文は258pxに縮んで
**スクロール可能**、スクロール後もヘッダーは画面内に残る。

**iOS Safari は未検証。** iOSはレイアウトビューポートを縮めず、キーボードが上に
重なる。ヘッダーを `position: sticky` にしてあるのはこの場合に保存を残すためだが、
**実機で確認していない。**

### 入れた挙動の変更（PCにも効く）

**二重送信ガード。** 以前は保存・削除中もボタンが生きており、2回押すと
`create` が2回走って予定が2件できた。`busyRef` で実際に止め、`busy` で
「保存中…」を出す。PCでも同じく無効化されるが、**機能は何も減っていない**。

### 未検証・持ち越し

- **iOS Safari のキーボード**（上記）
- 実機のタップ精度・慣性スクロール
- 320pxの日付ストリップのタップ領域39px（P8-b2からの持ち越し。**編集画面とは別の課題**）
- 日時ピッカーの `required`（**P8-b5**。今回は触らない）

## P8-b4: 共有・設定 — **完了（2026-10-18）**

### 画面ごとに形を選んだ

| 画面 | 720px未満 | 理由 |
| --- | --- | --- |
| 共有ダイアログ | **全画面シート**（`.sheet-*` を再利用） | 作成フォームの下に**件数に上限のないリスト**が続く。リンクが増えるほど「閉じる」が遠くなるので、閉じるをヘッダーに出す |
| 設定ダイアログ | **モーダルのまま**＋モバイル調整 | 2フィールドとアカウント1行。全画面にすると中身より枠のほうが大きい |

シートを機械的に使い回していない。設定をシートにしない判断のほうが、
揃えるより良い画面になる。

### 発見した二重実行（実測で確認）

**作成と失効にだけ再入ガードが無かった。** `deletingRef` / `togglingRef` は
最初から ref で守られており、その理由もコメントに書かれていたが、
`handleCreate` は `disabled={creating}` の**state だけ**、`handleRevoke` は
**何も無し**だった。

**実測**: ガードを外した版をビルドして「リンクを作成」を3連打 → **リンクが3件できた**。
ガードを戻して同じ操作 → **1件**。

作成が最も重いのは、**トークンが作成直後のバナーでしか見えない**ため。
2件目以降は有効なリンクとして存在するが、URLを知る方法が画面上に無い。

失効は `revokingRef` で**同じ行の再入のみ**を止めた。`busy` には入れていない
（`busy` は削除・切替がリスト差し替えと競合しないための別の役目で、広げると
今まで押せたボタンが押せなくなる＝今回の範囲外の挙動変更になる）。

実装していないキー操作を約束しないほうが、それに頼る人に対して正直。
